# Changelog

 * 2026-11-17: Added a Windows 11 Pro 26H2 (build 26300.9974) 32bit and 64bit import DB (`dbs/win11_pro_26h2_example.json`, 462 DLLs, 140,065 APIs), built with `DatabaseBuilder.py --paths C:\Windows\System32 C:\Windows\SysWOW64 --filter` on an installed system (not a fresh installation). All DLLs are Microsoft-signed system DLLs from `System32` and `SysWOW64`; the 7 DLLs the crawl also found in the `DriverStore` folder (copies shipped with driver packages) were removed afterwards. Like the other DBs of recent Windows versions, it carries the ASLR offsets of the boot it was built in and serves as example and for tests, not for dumps of other systems.
 * 2026-11-17: v3.0.0 - (BREAKING) Python 2 and IDA before 9.0 are no longer supported, and the scripts `scout.py`, `match.py`, `export.py`, `collect.py` and `update.py` are replaced by the `apiscout` command. Packaging moved to `pyproject.toml` (with `uv.lock`), code is linted and formatted with ruff and type checked with ty, CI runs on GitHub Actions, and a release published on GitHub is tested, built and uploaded to PyPI by a workflow (trusted publishing, with attestations).
   * Command line: `pip install apiscout` installs the `apiscout` command with the sub commands `scan`, `match`, `export`, `collect`, `update` and `dbs`. It prints JSON with `--json`, takes API DBs from `--db`, `--db-dir` or `$APISCOUT_DB_DIR`, reads and writes standard input and output with `-`, and its errors say what to do. `update` reads the Malpedia token from a file instead of `config.py`. `dbs download` fetches the example DBs of the repository for the installed version, checked against `dbs/SHA256SUMS`, into the user data folder, which is searched after `./dbs`; `--db` and `--collection` also find files there by bare name. (BREAKING) The JSON output changed shape: `scout.py -o` wrote a list of API rows, `apiscout scan --json` writes an object with these rows, unchanged, under `apis`, next to `base_address`, `api_dbs`, `apivector`, `apis_in_vector` and, with `--collection`, `collection_matches`.
   * Minidumps: `apiscout scan` recognizes a Windows minidump by its `MDMP` signature and scans its memory ranges (Memory64ListStream and MemoryListStream, adjacent ranges joined) at their own addresses with a small parser of its own (`apiscout/Minidump.py`, no new dependency, bounded by the size of the file), so offsets are virtual addresses (relative to `--base-addr` if given, which a file name no longer sets for a minidump). The processor architecture of a 32bit system restricts the search to 32bit pointers, and hits inside the images of the DLLs of the module list that are also in the API DB are left out, as they are the export tables and import address tables of the DLLs and not references of the sample. `ApiScout.crawlRegions()` scans regions like `ida_scout.py` does, and the references of a crawl result are now in the same coordinates as its offsets.
   * ASLR at scan time: one API DB per Windows build fits dumps of every boot. `apiscout scan --modules FILE` (lines of `<hex load address> <DLL path>`, the format and the matching rules of `DatabaseBuilder.py --load_addresses`, whose logic `apiscout/LoadAddresses.py` copies because the builder is standalone), the module list of a minidump, and DLL images found in a flat dump (PE headers at page-aligned offsets, identified by the name in their export directory and verified by the RVAs and ordinals of their exports, as the API DB stores no TimeDateStamp or SizeOfImage; the image at offset 0 is the sample's own and is skipped) place the DLLs of the API DBs at their real load addresses (`ApiScout.loadDbFile(path, place)`), the other DLLs keep the addresses of the DB. How many DLLs were placed from which source is reported on standard error and listed in `placed_dlls` of the JSON output.
   * Library: fixed a crash when a buffer ends in `FF 15`/`FF 25`, import tables (`apiscout scan --import-table`) are read by the own parser only, which gave the same imports as LIEF on all files tested and is bounded for crafted files, so LIEF is no longer a dependency, import descriptors without import name table, PE mapping of truncated or unusual files, matching of vectors given as lists, `NaN` when matching empty vectors, and API DBs of the same OS replacing each other. Crawl results are now ordered by offset. Imports by ordinal are resolved for `ws2_32.dll`, `wsock32.dll` and `oleaut32.dll`, compressed ApiVectors are validated, and a 32bit and a 64bit export at the same address are both resolved. Scanning is about 25 times faster: candidate addresses are searched with numpy (62 MB with two API DBs: 2.9 instead of 73 seconds), the results are the same.
   * Confidence: every hit of a scan gets a confidence from 0 to 100 against chance hits, bytes that happen to equal an API address. It adds up the evidence of the scan: hits in the import table are certain, otherwise other APIs within 16 bytes (an IAT or other table), calls and jumps through the location, another API DB agreeing and an offset aligned to the pointer size count. `apiscout scan --min-confidence N` drops hits below N (default 0 keeps all, the listing and the references are unchanged), the JSON records get a `confidence` field, and `ApiScout.getConfidences()` and `filterByConfidence()` are there for plugins. On the Malpedia dumps, 99.9% of the hits of the right API DB score 20 or more, while none of 1,786 chance hits (dumps scanned with DBs of other Windows versions, random buffers) do, among them the isolated `NdxTableAddObjectToList` of TrickBot.
   * The ApiQR export works again, the update works from any directory, and updating a collection no longer writes a second file.
   * IDA: `ida_scout.py` is a plugin now (see the README) with a dockable results view instead of a modal dialog, a batch mode and `ida-plugin.json` for the plugin manager. APIs are also annotated when their location was defined as something else before, type libraries match the bitness of the database and include ntapi, API locations are typed as function pointers, and the decompiler shows the API names for dumps loaded as binary file.
   * Binary Ninja: a plugin (`binja_scout`, `plugin.json`) scans the memory of a view with the chosen API DBs in a background task, lists the references found and annotates all of them or those with a neighbour within a given distance: import address symbols typed as pointers to the prototypes of the platform's type libraries. `apiscout.BinaryNinjaTools.scan_and_annotate()` does the same headless. Verified with Binary Ninja 6.0.10905 Ultimate on macOS 27.2 (menu, forms, report with address links, undo) and headless on memory dumps of Malpedia loaded as `Mapped` view with `win7_prof-n_sp1_example.json`: TrickBot (32bit) 182 of 183 references annotated, 179 with prototype; Cobalt Strike (64bit) 196 of 196 with prototype. Functions the linear sweep finds in tables of pointers and that nothing refers to are removed where a pointer is annotated (without this, 115 of the TrickBot references were skipped), `Zw*` APIs get the prototype of their `Nt*` counterpart, segments without data are not scanned, a cancelled scan keeps the results of the last one, and the extension manager, which imports the plugin as `apiscout.binja_scout`, finds it in the package.
   * Ghidra: `GhidraScout.java` is replaced by `ghidra_scout.py`, a script for PyGhidra (Ghidra 12 started with `pyghidraRun`) that calls the apiscout library instead of running ApiScout through temporary files, so apiscout is installed into the Python environment of PyGhidra. The script asks once for the folder with the API DBs (headless, its arguments are the API DBs only), scans the program's memory instead of the imported file, keeps all references to an API, annotates them like imports (external references and prototypes) and can be run headless (`pyghidraRun -H`).
   * License: the file headers named the GPL v3, while `LICENSE`, the package metadata and PyPI have said BSD 2-Clause since the first release. The headers now refer to `LICENSE` (`SPDX-License-Identifier: BSD-2-Clause`).
   * DB Builder: `--os_name`/`--os_version` build a DB from a copy of the DLLs on any OS, `--load_addresses` takes the ASLR offsets from a module list (lines of `<hex load address> <DLL path>`) instead of loading each DLL; DLLs are matched by folder and file name, or by file name alone where it is unique. The DLL filter covers DLLs of current Windows versions.
 * 2026-11-16: Added a Windows Server 2022 (21H2, build 20348) 64bit import DB (`dbs/win2022_server_21h2_example.json`, 343 DLLs, built with `DatabaseBuilder.py --filter` on a fresh installation). Like the Windows 10 DB, it carries the ASLR offsets of the boot it was built in and serves as example and for tests, not for dumps of other systems.
 * 2026-11-16: Follow-ups for the Windows 10 DB: `collect.py` now skips API DBs with ASLR offsets unless `--use_aslr_dbs` or `--ignore_aslr` is given (`FingerprintCrawler` got an `ignore_aslr_offsets` parameter) and loading a DB warns about many colliding addresses. ApiVector now matches DLL names case-insensitively (e.g. `IPHLPAPI.DLL`). Fixed `ws2_32.dll` being truncated in the JSON output of `scout.py`, missed references of 64bit `jmp [rip+x]` thunks, the base address of PE32+ headers and 64bit imports by ordinal. Tests now run with `unittest` instead of nose.
 * 2026-11-01: Added Windows 10 Pro 1803 (build 17134.1) 64bit import DB, including the ASLR offsets of the boot it was built in (as all 64bit system DLLs share the file ImageBase 0x180000000). These offsets are only valid for memory dumps from that very boot; for other dumps, use import table parsing (`scout.py -t`) or rebuild the DB on the system the dump was taken from. `scout.py --ignore_aslr` (`ApiScout.ignoreAslrOffsets(True)`) is only meaningful for systems without ASLR and not usable for this DB's 64bit DLLs, as they then overlap at 0x180000000. Also note that the offsets of several rarely loaded DLLs in this DB (mostly 32bit ones, e.g. iphlpapi.dll, wininet.dll) put them at overlapping addresses, so APIs of these DLLs may be resolved incorrectly. Also fixed two DB Builder bugs: version 0.0.0.0 was written for all DLLs, and ordinal-only exports were truncated for DLLs mapping many ordinals to one address (e.g. mfc42.dll lost ~90% of its exports).
